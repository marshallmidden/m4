# SFZ (sample-based) Orchestral Output — Implementation Plan (2026-09-03)

Status: PLAN (research done, no code written). Resumes from SFZ.md + this doc.

## Goal
Give the GCS→audio pipeline an option to render symphonies with real orchestral
**sample libraries** (SFZ format), dramatically better than the current
GeneralUser.sf2 GM synth, for Beethoven symphonies and Tchaikovsky 1812.

## Current pipeline (how it works today)
- `.gcs` → (gcc CPP) → `.E` → `imscomp --fluidsynth` → `.fs` (FluidSynth shell
  script of `noteon`/`noteoff`/`cc`/`sleep`/`select` text commands)
- `cat foo.fs | ~/bin/fluidsynth -F out.wav GeneralUser.sf2` (patched build for
  stdin→WAV render) → `gcs2youtube` wraps into `.mp4`
- Soundfont: GeneralUser.sf2 (GM synth — servicable but not a real orchestra)

## What SFZ gives us (vs SF2)
- TRUE stereo samples (SF2 is mono-only)
- Velocity layers (soft/loud per note)
- Round-robin (bow direction for strings)
- CC1 modwheel crossfade (timbre changes with dynamics, not just volume)
- Far better FREE libraries exist in SFZ than in SF2

## CORRECTIONS to SFZ.md (the prior google-dump)
The file is a decent starting point but has these issues:
1. **CLAP is irrelevant** — it's a plugin *host* standard, not a render target.
2. **Decent Sampler** — closed-source, no useful CLI; skip.
3. "MIDI 2.0" framing is misleading — SFZ is orthogonal to MIDI 2.0; we don't
   need MIDI 2.0 at all.
4. **Missing the key tool: `sfizz_render`** — the CLI renderer that makes
   SFZ+MIDI→WAV practical. This is the crux of the whole plan.
5. Missing **Sonatina Symphonic Orchestra** (CC0, CC1 dynamics).
6. Missing the biggest constraint: **MIDI channel/voice limit** (see below).

## THE CRITICAL CONSTRAINTS (the crux of the problem)
1. **MIDI 1.0 = 16 channels/port; only 15 usable for melody (0-8,10-15; 9=drums).**
   - `imscomp` already has `--midi1csv`/`--fluidsynth`; it bumps `MIDI_port`
     (to up to 16 logical ports × 16 channels) when it exceeds 16 melodic
     channels (`MAXMIDICHANNELS = 16`, line ~2212).
   - For `--midi1csv` it raises an error "puts midi channels > 16" then bumps
     MIDI_port (line ~5896).
2. **Beethoven symphonies and 1812 have MORE than 15 instruments.**
   - e.g. 1812 (`t/e/e`) has ~45 instrument types / 64 voices; Beethoven pieces
     are heavily orchestrated (20-29 distinct instruments typical; Beethoven 9
     pushes toward 30+).
3. Therefore a **standard single-port .mid cannot hold them all on distinct
   channels.** Options:
   - (A) **Reuse channels** — group instruments sharing the same SFZ program
         onto one channel; articulation/part separation is lost.
   - (B) **Multi-format / one .mid per staff** — but a normal .mid can't span
         ports (that's a General MIDI level-2/SMF2 idea, poorly supported).
   - (C) **Bypass .mid entirely — emit per-instrument SFZ play events directly.**
         Best for sfizz (below).

## RECOMMENDED ARCHITECTURE
Because of the >15 channel problem, the clean path is **NOT** going through a
standard .mid. Instead:

### Option C (RECOMMENDED): extension-format per-instrument render
- The compiler already has all events internally (notes with voiceon,
  instrument name, measure/time). Add a new output mode:
  `imscomp --sfzpipecsv` (SFZ-pipe CSV) or similar that writes, per voice/
  instrument, a plain text list of `(start_sec, dur_sec, midi_note, velocity)`
  lines. This sidesteps MIDI channels entirely.
- A new renderer (`gcs2sfz` or extend `gcs2youtube`) script:
  1. Maps each instrument name → an SFZ file (see `sfz/instruments.py` below).
  2. For each instrument, builds a minimal SFZ (or reuses the library's own
     .sfz) and a tiny .mid with those events → `sfizz_render --sfz X.sfz
     --midi X.mid --wav X.wav` (one render per instrument = unlimited count).
  3. Mixes the per-instrument stems: `ffmpeg -i stem_*.wav
     -filter_complex amix=inputs=N:duration=longest final.wav`.
  4. Wraps into `.mp4` exactly as gcs2youtube does now.

### Option A/B (simpler, less flexible fallback)
- Add `--midi1csv` → `.mid` conversion (csvmidi already exists) and render via
  sfizz, but RECYCLE channels: instruments with the same GM program share a
  channel. 1812's ~45 instruments collapse to the ~18 GM orchestral programs.
  Trade-off: can't have separate SFZ articulation/key-switch per part.

## sfizz (the SFZ player/engine)
- Open-source C++ SFZ synth: https://sfztools.github.io/sfizz/
- **`sfizz_render` CLI** (bundled):
  `sfizz_render --sfz inst.sfz --midi in.mid --wav out.wav`
  flags: `--samplerate`, `--quality`, `--polyphony`, `--oversampling`
- Build (if brew lacks sfizz_render): see SFZ.md / sfztools build docs.

## BEST ORCHESTRAL SFZ LIBRARIES (Beethoven + 1812)
Primary / recommended target order:
1. **VSCO2 Community Edition** (~3GB, CC0/public-domain) — best raw recording
   quality; has timpani/bass drum/snare/cymbals needed for 1812.
   https://github.com/sgossner/VSCO-2-CE/releases
2. **Virtual Playing Orchestra (VPO)** (~618MB, free non-commercial) — most
   complete out-of-the-box, every articulation mapped (sustain/staccato/
   pizzicato/tremolo). Combines VSCO2+Sonatina+Iowa+Philharmonia.
   http://virtualplaying.com/virtual-playing-orchestra/
3. **Sonatina Symphonic Orchestra** (~2.6GB, CC0) — CC1 dynamics crossfade,
   good string sections.
   https://github.com/peastman/sso

Special for 1812: cannon & church bells — NOT in any free SFZ lib. Need custom
one-shot WAV → trivial SFZ region (`<region> sample=cannon.wav key=...`).
